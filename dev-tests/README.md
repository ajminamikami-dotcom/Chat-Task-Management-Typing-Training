# デバッグ手順書 ─ チャットタスク管理・タイピングトレーニング

**対象**: チャットタスク管理_タイピングトレーニング.html（単一ファイル・Level 1〜3）
**土台**: OFFICE PULSE 品質要件体系 v1.0（バグ類型9種 / 品質要件96件 / 検査手法9種）をこのアプリ向けに翻訳したもの
**恒久検査スイート**: `dev-tests/` 配下 9本・約240項目（Playwright / Chromium、実アプリを利用者と同じ操作で駆動）

## 0. この文書について

OFFICE PULSE で確立した「バグを個別修正で終わらせず、**二度と起こさないための不変条件**として言語化し、自動検査に変換する」やり方を、このアプリに適用した記録と手順です。

このアプリは OFFICE PULSE より構造が小さい（PP・ランク・メール・日報が無い）ため、96要件のうち**このアプリに意味を持つ要件だけを選び**、このアプリの言葉で書き直しています。汎用IDは元の体系と同じものを使っているので、他アプリと突き合わせできます。

```
① バグ類型(9種)     … このアプリでの「壊れ方」の具体例          → §1
      ↓
② 品質要件(45件)    … 「常に成り立つ」不変条件（アプリの言葉で） → §2
      ↓
③ 検査スイート(9本) … 要件を機械的に検証する                     → §3・§4
```

**最優先はプレイアビリティ**です。「どう操作しても、バグで進めなくなることがない」を、無作為操作×解決可能性オラクル（e2e03）と模擬プレイ（e2e01）で構造的に保証します。

## 1. このアプリで狙う壊れ方（バグ類型9種）

| # | 類型 | このアプリでの意味 | 実際に見つかった例 |
|---|---|---|---|
| 1 | **状態喪失** | 画面切替・再描画・電話・一時停止で、入力途中の返信文や選んだ優先度が消える | 新着で受信トレイが再描画されると、キーボード操作中のフォーカスが飛ぶ（V6で修正） |
| 2 | **評価の因果切断** | 正しい操作が報われない／何もしないのに点がつく／内訳と総数が合わない | 「平均処理」が常に0.0秒。完了0件で「0%」（全問不正解に見える）。電話の誤答が「よかった点」に載る |
| 3 | **分岐非対称性** | 返信要と返信不要、Level 1と2/3、マウスとキーボードで、フェーズや判定タイミングが違う | 「返信不要」の3問だけ選択肢が1個（選択肢数で正解が漏れる） |
| 4 | **後知恵評価** | 届いていない情報を根拠に減点する | 該当なし（判定に必要な情報はすべて本文にある） |
| 5 | **指示の実行不能化** | 出題時は解けた課題が、状況変化で解けなくなる | 該当なし |
| 6 | **クリア不能・理不尽** | 正しく操作しても最高評価に届かない／人間的に不可能な猶予 | 優先度を一度選ぶと選び直せない（誤クリックが確定）。電話が30秒ごとに鳴りタイピングが成立しない。「すぐ再提出します」が不正解 |
| 7 | **再入・二重計上** | 連打・二重終了・古いUIで記録が重複する | 時間切れと「送信」クリックが同じ瞬間に起きると、集計後にチャットが完了扱いになりCSVと画面が食い違う（V6で修正） |
| 8 | **参照の曖昧性** | 一覧や指示が対象を一意に特定できない | 受信トレイに「総務部」が2件並ぶ |
| 9 | **罰の複利化** | 1つの誤りが複数箇所で減点される | 該当なし（優先度と返信は独立に1回だけ判定される ─ e2e08 CO で確認） |

### 類型が示す設計原則（このアプリ版）

- 類型1・7 → **状態の所有者と有効期間を明示せよ**: 下書きは `chat.draft` に持ち、再描画では必ず復元する。`gameOver` 後はすべての操作を無効にする
- 類型2・6・9 → **評価は行動の証拠だけに基づき、機会がなければ分母から外せ**: 未完了は分母に入れない。電話が鳴らなければ「-」
- 類型3・8 → **同じものは同じ形で、違うものは違う名前で**: 返信要/不要で同じ3択、送信者名は一意
- 類型4・5 → 該当構造なし。ただし**解決可能性は未完了の間ずっと維持**（e2e03 のオラクルで毎ステップ確認）

## 4. 実行方法

```bash
cd dev-tests
npm install                    # playwright を入れる（初回のみ）。既にグローバルにある場合は NODE_PATH でも可
node run-all.js                # 全9本（約55分）
QUICK=1 node run-all.js        # 長時間スイートを除く（約5分）: 07, 03, 05, 06
ONLY=e2e03,e2e07 node run-all.js
```

| 個別実行 | 主なオプション |
|---|---|
| `node e2e03_softlock.js` | `ROUNDS=3 STEPS=120`（高速）／`LEVELS=2,3 STEP_DELAY=600 STEPS=160`（電話・新着を発生させる低速版）／`SEED=` |
| `node e2e08_judgment.js` | なし（約25分。Level 2 は全20件が届くまで待つ） |
| `node e2e01_playthrough.js` | なし（約8分。Level 2 は5分の時間切れを待つ） |
| 全スイート共通 | `APP=path/to/app.html` で対象ファイルを差し替え可 |

- テストは本体を**一時コピー**して動かします。本体ファイルを書き換えることはありません
- 結果は `_out/<suite>.json` と、`_out/*.csv`（アプリが出力したCSV）に残ります
- 検証は**利用者と同じ操作**（クリック・キー入力）で行い、内部状態の直接書き換えはしません。時間切れも実時間で待ちます

## 5. 運用手順

### 5-1. 1ラウンドの型（必ずこの順序で）

1. **要件定義** ─ 検査観点を「〜が常に成り立つ」の1〜2文で書く。§2 の表に行を足す
2. **専用の自動テストを作成** ─ 該当スイートに `R.ok("ID", 条件, "説明")` を足す。操作は利用者経路で
3. **切り分け** ─ 落ちたら「テストの不備」か「実バグ」かを必ず切り分ける。
   例: e2e08 初回で Level 2 に6件のNG → 調べると**同じ本文が Level 1 と 2/3 の両方にあり、テストが Level 1 側（お手本なし）を引いていた**。アプリは正しかった。テストの `findAnswer` にレベルを渡すよう修正
4. **バグは本体を直す** ─ テストを緩めない。原因を特定して本体を直し、修正理由をコメントに残す
5. **全回帰** ─ `node run-all.js`。仕様変更でテストが落ちた場合のみ、理由を明記して新仕様に更新
6. **文書化** ─ §6 に 現象/原因/影響/修正/類型/要件 を追記

### 5-2. 場面別の着手点

| 場面 | まず実行する検査 |
|---|---|
| 利用者から「進めなくなった」 | 報告の操作列を e2e03 の `randomAction` に固定シーケンスとして再現 → e2e03 全レベル → 一般化して §2-1 に要件化 |
| 利用者から「正解のはずが不正解」 | e2e08（判定マトリクス）→ e2e07 AA（判別可能性）。正解表と本文の両方を疑う |
| 問題データ（LEVEL1_DATA / TYPING_DATA / PHONE_DATA）を変えた | **e2e07 → e2e08 → e2e02** の順。e2e07 が落ちたらデータを直す（判別できない罠を作らない） |
| 採点・結果画面を変えた | e2e08, e2e01（独立再計算）, e2e02 |
| 進行・タイマー・電話・一時停止を変えた | e2e03（高速+低速）, e2e04, e2e01 |
| UI・CSS・文言を変えた | e2e05 AE（画面幅）, e2e06（対称性）, e2e04 AB（文字列走査） |
| マニュアルを変えた | 本体の文言（判定基準パネル・ラベル）と食い違わないか目視。§2 の要件IDで対応づける |
| リリース前 | `node run-all.js` 全8本合格 + ZIPから展開した状態で e2e07 F-1〜F-4（単一ファイル・埋め込みロゴ） |

### 5-3. 報告様式

- バグごとに **現象 / 原因 / 影響 / 修正内容 / 該当する要件ID・類型**
- 修正が利用者の体験を変える場合は、**専門用語を使わない平易な説明**を併記（配布ZIPの「修正内容.txt」に転記）
- ラウンドの最後に「検査項目と結果」の表と回帰結果を要約する（§7）
- **「テストの不備だった」も記録する**。切り分けの実例が次のラウンドの精度を上げる
