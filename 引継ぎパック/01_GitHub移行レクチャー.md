# 1. GitHub への移行と、日々の作業の流れ（レクチャー）

このテキストは、アプリの管理・デバッグを引き継ぐ方に向けて、**開発環境を GitHub に移すところから**順に説明します。
プログラミングの経験がなくても、上から順にやれば GitHub 上のファイルを自分の PC に取り込み、検査を回し、変更を記録して戻せるようになります。

> 大事な前提: **本体は 1 つの HTML ファイルです。分割も縮小もしません。** AI ツールの貼り付け上限が足りないときは、ファイルを小さくするのではなく、GitHub 上のファイルを AI に読ませる（この文書の 5 章）か、「断片」フォルダのコピーを使います（本体には一切手を加えません）。

## 1-3. GitHub Desktop でリポジトリを PC に取り込む（クローン）

1. GitHub Desktop を起動し、`File → Options → Accounts` で GitHub にサインインします。
2. `File → Clone repository…` を開き、`URL` タブに `ajminamikami-dotcom/Chat-Task-Management-Typing-Training` を入れます。
3. `Local path`（保存先）は、**日本語や空白を含まないフォルダ**にしてください（例: `C:\work\chat-training`）。日本語パスでも動くことが多いのですが、Node やブラウザまわりのトラブルを避けられます。
4. `Clone` を押します。終わると左上に `Current repository` としてこのリポジトリが出ます。
5. 上部の `Current branch` を押し、`claude/bug-check-ifi5ym` を選びます（`main` に取り込み済みなら `main` のまま）。
6. エクスプローラーで保存先を開き、`チャットタスク管理_タイピングトレーニング.html` をダブルクリックすると本体が起動します。これが「いまの最新版」です。

> **用語**: クローン＝GitHub のコピーを PC に作ること。フェッチ／プル＝GitHub 側の新しい変更を PC に取り込むこと。コミット＝変更をひとまとめにして記録すること。プッシュ＝コミットを GitHub に送ること。

## 1-4. 検査（dev-tests）を動かせるようにする

本体の変更は、必ず検査で確かめてから保存します。初回だけ準備が要ります。

1. Node.js（LTS）をインストールします。インストール後、PC を再起動すると確実です。
2. 保存先フォルダの `dev-tests` を開き、アドレスバーに `cmd` と打って Enter（そのフォルダでコマンドプロンプトが開きます）。
3. 次を 1 行ずつ実行します（初回のみ）。

```bat
npm install
npx playwright install chromium
```

   `npm install` が検査ライブラリ（Playwright）を、`npx playwright install chromium` が検査用のブラウザ（約 150 MB）を入れます。会社のネットワークで止まる場合は、自宅回線やスマホのテザリングで一度だけ通してください。

4. 動作確認（約 6 分）:

```bat
set QUICK=1
node run-all.js
```

   最後に各スイートの `== e2e07_data: 28/28 OK …` のような行が並び、`PASS` が揃えば準備完了です。1 本でも `NG` があれば、変更前の状態で既に赤いということなので、「5. 困ったとき」を見てください。

> 全部の検査（`node run-all.js` だけ）は約 60 分、変異検査（`node mutate.js`）は約 1.5〜2 時間かかります。日々の変更では QUICK で十分で、版を上げて配る前に全部を回します。

## 1-5. 日々の作業の型（必ずこの順序で）

```
① Fetch origin（GitHub 側の最新を取り込む）
② 変更する（本体 HTML／問題データ／文言／検査）
③ 検査を回す（QUICK → 必要なら全部）
④ GitHub Desktop で変更内容を確認し、要約を書いてコミット
⑤ Push origin（GitHub に送る）
```

- **①** GitHub Desktop 上部の `Fetch origin` を押し、`Pull origin` に変わったらもう一度押します。他の人の変更を取り込んでから作業を始めます。
- **②** 1 回の変更は 1 つの目的に絞ります（文言の修正と時間の変更を同時にしない）。どこを変えるかは `02_コードの地図` と `04_よくある作業の手順` を見ます。
- **③** `set QUICK=1` → `node run-all.js`。赤くなったら、変更を戻すか原因を直すまで次に進みません。検査の読み方は `05_検査の実行方法` にあります。
- **④** GitHub Desktop の左側に変更したファイルが並び、右側に差分（赤＝消えた行、緑＝増えた行）が出ます。**自分が変えたつもりのない行が緑や赤になっていないか**をここで確認します。左下の `Summary` に「何を・なぜ」を日本語で 1 行（例: `B社の本文に至急の語を追加（判定基準から高が導けるように）`）、必要なら `Description` に検査結果（`QUICK 7本 PASS` など）を書き、`Commit to <ブランチ名>` を押します。
- **⑤** 上部の `Push origin` を押します。これで GitHub に保存され、他の PC からも取り込めます。

> **やってはいけないこと**: 検査を回さずにプッシュする／検査を通すために検査側を弱める（`dev-tests/README.md` 5-1 の「切り分け」に従う）／`golden.js --update` を差分を読まずに実行する／本体を複数ファイルに分割する。

## 1-6. ブランチを `main` に取り込む（引き継ぎ時に一度だけ）

1. GitHub のリポジトリページを開き、`Pull requests` → `New pull request`。
2. `base: main` ← `compare: claude/bug-check-ifi5ym` を選び、`Create pull request`。タイトルは「V5 と検査一式を main に取り込む」で十分です。
3. 作成したプルリクエストの画面で `Merge pull request` → `Confirm merge`。
4. GitHub Desktop に戻り、`Current branch` を `main` にして `Fetch origin`／`Pull origin`。`main` に本体・dev-tests・配布物・引継ぎパックが揃っていれば完了です。
5. 以後の作業は `main` で行うか、作業ごとに `Current branch → New branch` で枝を作って、終わったらプルリクエストで `main` に戻します（枝を使うと、途中の状態を `main` に混ぜずに済みます）。

> `main` に残っている最初の ZIP（`☆【最新】…-20260907….zip`、約 8 MB）は履歴として置いてあるだけです。消しても本体の動作には関係ありません。

## 1-7. 版を上げて配る（配布 ZIP）

1. 本体のタイトル（`<title>` と開始画面の表記）は現在 `V6` のままにしています。配布 ZIP のフォルダ名と説明書の版（V5 など）が「配布の版」です。両方を同時に上げる場合は `04_よくある作業の手順` の「版を上げる」を見てください。
2. 説明書 `配布物/【V6 ○○】.txt` を書きます（前の版 `【V5 一本化の確認】.txt` を複製して書き換えると楽です）。
3. リポジトリの直下でコマンドプロンプトを開き、次を実行します。

```bat
python 配布物\build_zip.py V6 "配布物\【V6 ○○】.txt"
```

   `配布物\out\☆チャットタスク管理・タイピングトレーニング V6.zip` ができます（本体・マニュアル・説明書・dev-tests・引継ぎパックを同梱）。Python が無い PC では、同じ構成のフォルダを手で作って ZIP にしても構いません（ファイル名が日本語なので、Windows 標準の「圧縮」で作ったものは Mac で文字化けすることがあります）。
4. `out/` フォルダは Git に記録されません（`.gitignore`）。配布 ZIP は GitHub の `Releases` に添付するか、共有ドライブに置きます。

## 1-8. 実施マニュアル（Word / PDF）を直す

- 元ファイルは `配布物/…実施マニュアル_編集用.docx` です。Word で直して保存し、`PDF としてエクスポート`（Word の `ファイル → エクスポート`）で PDF を作り直して、両方をコミットします。
- **判定基準の文言は、本体の開始画面「判定基準」パネルと同じ言葉にします。** パネルの文言は仕様書（`dev-tests/spec/judgment-spec.md` §11）と検査（`e2e07` の P-8）で縛られているので、先に本体とパネルを直し、最後にマニュアルを合わせる順番が安全です。
- マニュアルの画面写真は、本体を 1366 幅で開いて撮ります（この引継ぎの時点で V5 の画面に撮り直してあります）。

## 1-9. 困ったときの連絡先と記録

- 変更の記録は GitHub のコミット履歴（`History`）がそのまま台帳になります。問い合わせや不具合は GitHub の `Issues` に 1 件ずつ書くと、AI ツールにそのまま貼れる形で残ります（`08_不具合対応の記録と判断基準` の様式）。
- この引継ぎパックの各文書は、`引継ぎパック/` の番号順に読むことを想定しています。最初に `00_はじめに.md` を読んでください。
